---
description: Report or progress the project through the deterministic Engineering Harness bootstrap lifecycle
argument-hint: "[status]"
---

Act only as the Claude Code adapter to the deterministic Engineering Harness core.

1. Read `CLAUDE.md`.
2. Locate the Harness core from the developer environment, never by guessing: the core is the command held in `ENGINEERING_HARNESS_CORE`, run from the project root (for example `../harness-core`); when the variable is unset, use `engineering-harness` on PATH. `init` records the value in `.claude/settings.json`. The core resolves the Harness root by itself (`ENGINEERING_HARNESS_ROOT`, otherwise the `_root` directory beside the binary); never pass a root and never look for one. If the core exits 64, stop and report its message.
3. For `status`, invoke the core's `inspect_project` operation for the current project and render its structured result. Do not derive state yourself. `status` never writes anything.
4. Without `status`, first inspect the project. If the core reports lifecycle state `PROJECT_INPUT_REQUIRED` and `project-pack/PROJECT-PACK-BRIEF.md` exists, that brief is the operator's explicit written instruction: complete `project-pack/` by following it exactly, re-run `inspect_project` after every change, and stop when the state is `PROJECT_INPUT_READY`. Without a brief, stop for `HUMAN_INPUT`. This is the only case in which this command writes under `project-pack/`.
5. When the core's next action is an AI-assisted operation (BRS §34) you are the author of its input for `ingest_specification`, `derive_architecture` and `generate_work_items`; `derive_project_ai_policy` takes no input document. The core only decides whether the operation is permitted, validates the document against the release schema and writes it into the governed location.
   - Draft the document from the Pack's declared authoritative sources under `project-pack/source/` and from any baselined predecessor (a baselined specification for the architecture, a baselined architecture and specification for the work items). Do not filter, reprioritise or invent content: one requirement per requirement stated in the sources; unresolved points go into `ambiguities`; stated assumptions go into `assumptions`.
   - Write the draft to a temporary file outside the project. Never write under `project-pack/`, `spec/`, `architecture/`, `ai/`, `work/` or `engineering/` yourself.
   - Run the operation exactly as the core's usage shows, passing the draft with `--file` (a single document) or `--dir` (a document set). If the core's usage does not offer the operation, stop and report that; do not place documents in governed directories by hand.
   - For `ingest_specification` the document is `schema://intent/specification/v1`: `schema_version: 1` and a `specification` object with `id`, `title`, `requirements[]` (each `id`, `statement`, `source_refs` listing source ids declared in `project-pack/source/manifest.yaml`), `acceptance_criteria[]` (each `id`, `requirement_id`, `statement`), and optional `assumptions[]` and `ambiguities[]` of strings. `validate_specification` rejects duplicate ids, a criterion that references an unknown requirement, a requirement with no criterion, and a `source_refs` entry that is not a declared source.
   - For `derive_architecture` the input is a directory laid out like the project's `architecture/`, passed with `--dir`: `architecture.yaml` (`schema://intent/architecture/v1`: `architecture` with `id`, `title`, `components[]` each `id` starting `COMP-`, `name`, `responsibility`, `requirement_refs`; plus top-level `requirement_refs`, `adr_refs`, `contract_refs`), `adrs/<ADR-id>.yaml` (`schema://intent/adr/v1`: `adr` with `id` starting `ADR-`, `title`, `status` of `proposed|accepted|superseded`, `decision`, `rationale`, `requirement_refs`) and `contracts/<CONTRACT-id>.yaml` (`schema://intent/contract-reference/v1`: `contract` with `id` starting `CONTRACT-`, `name`, `type` of `api|event|data|integration|other`, `requirement_refs`). Derive it from the baselined specification in `spec/specification.yaml`: every requirement must be allocated to at least one component, every `requirement_refs` entry must be a requirement id from that specification, every ADR and contract file must be named `<id>.yaml` and be listed in `adr_refs` / `contract_refs`. `validate_architecture` enforces exactly those rules.
   - For `derive_project_ai_policy` there is nothing to draft: the core derives `ai/policy.yaml` (`schema://project-state/ai-policy/v1`) from the effective policy controls in `engineering/controls.yaml` and the current Architecture Baseline (BRS §20.3, §31). Run it with no `--file` or `--dir`. It is idempotent; once the policy is current the core reports `generate_work_items` as the next action.
   - For `generate_work_items` the input is a directory laid out like the project's `work/`, passed with `--dir`: `tasks/<TASK-id>.yaml` (`schema://work/item/v1`: `work_item` with `id` starting `TASK-`, `title`, `requirement_refs`, `acceptance_refs`, `architecture_refs` (component `COMP-` or `ADR-` ids), `contract_refs`, `dependencies` (task ids), `repository_scope` (`schema://work/repository-scope/v1`: `allowed` and `forbidden` path patterns), `verification_controls` (control ids taken from `engineering/controls.yaml`), `human_gates` (gate ids of the release, or empty)) and `execution-graph.yaml` (`schema://work/execution-graph/v1`: `execution_graph.tasks[]`, each `id` and `depends_on` equal to that task's `dependencies`). Derive it from the baselined architecture under `architecture/` and the baselined specification in `spec/specification.yaml`. `validate_work_graph` enforces exactly these rules: every task file is named `<id>.yaml` and ids are unique; the graph lists exactly the task files; every dependency names an existing task and a task's `dependencies` equal its `depends_on`; the graph is acyclic; every requirement, acceptance-criterion, component, ADR and contract reference resolves; every requirement and every acceptance criterion of the specification is covered by at least one task; every `repository_scope` path stays inside the repository (no `..`, no absolute paths) and `allowed` never enters `project-pack/`, `spec/`, `architecture/`, `engineering/`, `ai/`, `work/tasks/`, `work/execution-graph.yaml`, `baselines/`, `evidence/validation/`, `evidence/candidates/` or `evidence/approvals/`; implementation scope lives under `src/`, `tests/` and `infra/`. Scale: never write one task per requirement. Write one task per component (or per group of closely related components) whose `requirement_refs` are that component's requirements and whose `acceptance_refs` are every acceptance criterion of those requirements; a 200-requirement specification then yields roughly as many tasks as components while still covering every criterion.
6. After an AI-assisted operation succeeds, inspect again and keep performing the deterministic next actions the core reports (such as `validate_specification`) until it reports a `HUMAN_DECISION`. Stop there: present `pending_gate.gate`, `pending_gate.candidate_path` and `pending_gate.candidate_digest` from the result, and the short form of the decision command the operator has to run: `<core> approve_pending --project-root . --approver <identity> --pretty`, where `<identity>` is the identity assigned in `project-pack/project.yaml` to the gate's authority (a rejection is `<core> reject_pending --project-root . --approver <identity> --comment <reason>`). The equivalent long form is `record_*_decision --decision approved --approver <identity> --authority <gate authority> --expected-candidate <candidate digest>`. Never record a decision yourself: never run `approve_pending`, `reject_pending` or `record_*_decision`. When the core reports `EXECUTION_READY` with next action `none_bootstrap_complete`, bootstrap is complete: report it and stop. Never execute a Work Item from this command; Work Items are executed with `/execute`.
7. Otherwise perform only the single next action returned by the core, and only when that action is an operation this adapter is authorised to perform.
8. Stop for `HUMAN_INPUT`, `HUMAN_DECISION`, `REWORK`, `BLOCKED`, `INVALID`, or `ERROR` outcomes and present the exact issue codes and next action.
9. Never create approval decisions (neither `record_*_decision` nor `approve_pending` / `reject_pending`), broaden write scope, alter `/project-pack` except under step 4, write governed documents except through the core under step 5, or silently choose/download a Harness release.

The adapter must not claim a lifecycle transition that the deterministic core does not support from repository evidence.
